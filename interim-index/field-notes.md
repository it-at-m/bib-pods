# Field notes: mapping MSB's MARC data to a Solr index

> Generated by Claude Code, based on the `interim-index/` implementation and measurements against the full OAI dump and the live interim index.

Everything we learned building the interim index, written down for whoever builds the
production Solr index. It covers what we map and why, what we deliberately don't map
(with the measurements behind each decision), quirks of the Münchner Stadtbibliothek
(MSB) data that a production mapping must handle, and what consumers of the index rely
on. All numbers were measured in July 2026 against the full OAI dump (~26,000 page
files) and the live interim index (1,262,881 records); treat them as that snapshot.

The mapping itself lives in [`shared.js`](./shared.js) (`mapRecord`), shared by the
importers. Field names deliberately follow VuFind's standard
[marc.properties](https://github.com/vufind-org/vufind/blob/dev/import/marc.properties)
mappings — if the production index is VuFind-based (or wants to stay compatible with
its ecosystem), the naming carries over as-is.

## 1. The source data

- **OAI-PMH** MARC21 XML from `data-bib.muenchen.de`, exported by MSB's aDIS/BMS
  library system. Records deleted in the catalogue arrive as OAI deletion markers
  (`header/@status="deleted"`) and must be deleted from the index by their
  `oai_identifier` — an importer without a delete handler accumulates stale records.
- **Record id** = MARC 001, `AK` + digits (e.g. `AK4298169`). The public SOPAC
  catalogue URL wants `SAK` + the digits zero-padded to 8 (`sp=SAK04298169`); the
  inspira recommender wants the bare digits without `AK`. Keep the 001 form as the
  index id — everything else derives from it.
- **OAI setSpec** (mapped to `institution`): every record carries the ISIL `DE-M36`;
  ~38% additionally carry a sub-collection set (`DE-M36:DE-M36b` 250k,
  `…:DE-M36e` 146k, `…:DE-M36d` 57k, `…:DE-M36c` 25k). We never resolved what
  b/c/d/e denote — worth asking MSB; if they mean branch/collection they enable
  "available at my branch" features.
- Tag frequency across a 13k-record spread sample, for orientation (per-record
  presence): 245 100%, 264 99%, 336/337/338 ~95–98%, 876 90%, 300 90%, 100 59%,
  041 52%, 020 37%, 700 33%, 655 25%, 689 22%, 650 21%, 250 22%, 520 18%, 490 15%,
  024 14%, 830 12%, 500 10%, 240 9%, 521 8.5%, 028 7%, 651 7%, 856 7%, 600 4%,
  648 3%, 710 3%, 546 2%, 505 2%, 800 2%.

## 2. Mapping conventions worth keeping

### Authority IRIs are minted at index time

Every label-carrying subject/author field has a parallel `*_uri_str_mv` field with a
**resolvable IRI** minted from `$0` + `$2` (base URI per vocabulary: GND, LCSH, FAST).
Rationale: consumers should never have to know that `(DE-588)4211695-8` means
"GND number" — the indexer resolves that once.

- MSB regularly omits `$2` on 1xx/6xx/7xx but always writes `(DE-588)…` numbers;
  DE-588 is the GND's own MARC organization code, so the mapping infers GND from
  that prefix as a dataset-specific fallback. **Production must keep this fallback**
  or lose most authority links.
- Entries without a resolvable IRI get the sentinel `https://unknown.invalid/`
  (RFC 2606 `.invalid`, guaranteed unresolvable) — **not** the empty string, because
  Solr's JSON update handler silently drops empty strings from multiValued arrays.
- **Positional alignment is a contract**: `author2_uri_str_mv[i]` is always about
  `author2[i]`. The label and URI arrays are built by walking the same datafields in
  document order. Consumers (e.g. the plugin's book-click follow-up dialog) zip the
  two arrays by index.

### MSB/German-specific handling

- **Medium**: MSB writes a human-readable medium designator in 245$h
  (`[Druckschrift]`, `[E-Book]`, `[CD]`, `[Buch + CD]`, …; brackets are GMD/ISBD
  convention and are stripped) → `format`. The machine-readable counterpart is the
  RDA carrier from 338 (`$2=rdacarrier`), minted as LoC IRIs
  (`https://id.loc.gov/vocabulary/carriers/<code>`) → `format_uri_str_mv`, plus
  `electronic` = carrier `cr` (online resource). 79 distinct `format` values;
  Druckschrift 913k, Noten 113k, CD 80k, E-Book 34k, DVD-Video 22k, ….
- **Onleihe**: 856$u links of the form `…onleihe.de/…/mediaInfo,<x>-<y>-<mediaId>-…`
  carry the divibib media id → `onleihe_id`. Not guaranteed unique (the same holding
  is occasionally catalogued twice), but duplicates share bibliographic data, so any
  match is a valid resolution. This field is what lets a click on an Onleihe link on
  the website resolve to its catalogue record.
- **Author name form**: 100/700 arrive as `"Lastname, Firstname YYYY-YYYY"`. The
  index stores them raw (VuFind convention); display-side cleanup (drop dates, swap
  to natural order) happens in the consumer. A production index may prefer to also
  store a cleaned display form.
- **Titles**: trailing ISBD punctuation (`" /"`, `" :"`) is stripped from 245a/b.
  Some titles carry `" | <marketing subtitle>"` appendices; the interim index keeps
  them (consumers split on `" | "` for display).
- **Series**: 800/830 carry `$w` (control number of the linked series authority,
  e.g. `(DE-M36)AK1120883`) which is *alphabetic* and would leak into display strings
  if mapped naively with an all-alpha-subfields rule — 800 uses `abcdfpqt`, 830 `ap`.
  That `$w` link could one day resolve series membership properly.

## 4. Measured quality of the subject fields

The headline: **topics are excellently GND-linked, genres are effectively not linked
at all.** Details (docs carrying the field / docs with at least one unresolvable
entry):

- **topic**: 314,829 docs; only 1.5% carry an unresolvable entry; ~49,000 distinct
  GND IRIs, ~56,000 distinct labels. The strongest symbolic-recommendation substrate
  in the index.
- **author**: 730,869 docs; 17.4% (of all docs) carry an unresolvable author →
  roughly 70% of authored records have a GND-linked main author; ~112,000 distinct
  author IRIs.
- **genre**: 319,574 docs, but only ~760 docs across **6 distinct** genre IRIs
  resolve to GND — MSB's 655 fields simply don't carry `$0`. Genre is a
  **label-only** field: 959 distinct values, extremely head-heavy (Musikdruck 106k,
  Musiktonträger 76k, then Führer 10k, Aufsatzsammlung, Kindersachbuch, …).
  Note the head is polluted by carrier-like values (Musikdruck, CD) — a curated
  genre list for user-facing purposes should filter those.
- **geographic**: 95,229 docs, only 0.5% unresolvable; 8.8k distinct values
  (Deutschland 19k, München 4.9k, Bayern 3.2k, …).
- **era**: 44,963 docs, **zero** resolvable IRIs, 11.6k distinct values that are
  mostly free-form time phrases ("Geschichte 1933-1945"). Only useful if someone
  parses the year ranges; not worth authority treatment.
- **language**: 256 distinct codes, but `unb` (undetermined) covers 49% of the whole
  index — essentially the sheet-music and audio stock; `ger` 515k, `eng` 105k,
  `fre` 23k, `ita` 13k, `spa` 10k. Filters on language must expect `unb`.

## 5. What we deliberately do NOT map — and when to revisit

### RSWK Schlagwortfolgen (689) — measured, decided against

689 carries the German subject-heading chains: `$D`-coded authority-linked terms
(s Sachbegriff, p Person, b Körperschaft, g Geografikum, u Werk, n Familie) with the
GND number in `$0`, and `$A`-coded authority-free terms (f Formschlagwort,
z Zeitschlagwort) without `$0`. `$A` and `$D` never co-occur; `$5` names the
assigning library (DE-M36).

They look like gold — 22% of records, ~3.9 terms each — but **MSB's aDIS export
already materializes every chain term as a classic 6xx heading** (s/p/b/u/n → 6xx
topic fields, g → 651, z → 648, f → 655). Measured on a spread sample of the full
dump (21,045 records): 99.1% of 689 terms duplicate a same-family 6xx label or GND
number of their own record; mapping-and-deduplicating them changed 128 docs (0.6%),
added zero new GND links, and the gained terms were mostly qualifier variants
("Dresden <1993>" next to an existing "Dresden 1993"). We reverted the
implementation as not worth its code.

**Revisit if** the export ever stops materializing chains into 6xx (symptom: topic
coverage drops while 689 stays), or if a production source other than this OAI export
is used. The routing that was implemented and verified: `$D g` → geographic,
`$A z` → era, `$A f` → genre, everything else → topic; dedup pairwise against the
6xx-derived label+IRI arrays.

### Content and media type (336/337) — recommended for production

The index knows the *carrier* (338 → `format`) but not *what kind of content* is on
it. The case that matters: `format:"CD"` (80k records) mixes music CDs and
audiobooks with no way to tell them apart. 336 (`$2=rdacontent`) is the discriminator:
Text, gesprochenes Wort (= audiobook), aufgeführte Musik, Noten, unbewegtes Bild,
zweidimensionales bewegtes Bild, …. 337 (`$2=rdamedia`) is the third RDA axis
(ohne Hilfsmittel zu benutzen / audio / Computermedien / video / Mikroform).
Recipe: mirror the 338 handling — label from `$a`, LoC IRI from `$b`
(`https://id.loc.gov/vocabulary/contentTypes/<code>`, e.g. `spw` for spoken word).
This is what makes a "Hörbuch" preference expressible.

### Audience / age recommendation (521) — recommended for production

8.5% of records (concentrated in children's media, where it counts) carry 521$a, and
in a 2,220-field sample **every single value** matched the exact pattern `ab <N>`
("ab 4", "ab 12", …). A clean, directly filterable age-band facet for kids/family
features. One-line mapping.

### Blurbs (520) — inline half is a one-liner, the rest is a crawl decision

Three kinds, measured: **~50% inline German text** in `$a` (real publisher blurbs —
indexable as a `summary` field immediately); **~35% URLs to
`deposit.dnb.de/cgi-bin/dokserv?…`** — small HTML pages hosted by the DNB containing
the publisher's Verlagsmeldung blurb (verified by fetching; harvestable as text, but
that's a batch crawl of ~100k+ URLs with politeness/licensing questions — a separate
decision); **~13% `d-nb.info/<idn>/04` links** which are scanned tables of contents
as PDFs (not worth pursuing); the rest junk (publisher homepages). Blurb text is
also what the inspira_BIB embedding recommender is built on — an indexed `summary`
field would be the substrate for any in-house semantic similarity.

### Other unmapped tags, briefly

- **035**: system control numbers, including sub-institution variants of the same AK
  id (`(DE-M36:DE-M36b)AK…`) — the raw material for understanding the DE-M36b/c/d/e
  sub-collections.
- **876**: present on 90% of records but carries only a numeric `$t` in our data
  (likely copy count). Unexplored; item-level data would normally live here.
- **024**: EAN/ISBN-13-like identifiers without `$2` (14%). Redundant with 020 for
  books; possibly useful for non-book media matching.
- **500/546/518/505 etc.**: notes fields; 505 (contents) is mapped, the rest are
  low-coverage prose.
- **No classification at all**: the records carry no 082/083/084 (DDC or
  GND-Sachgruppen). Consequence: coarse subject categories ("Themenbereiche") cannot
  come from the records. If wanted, they can be derived: GND authority records link
  each subject to its GND-Sachgruppe (`gndSubjectCategory`), so an enrichment pass
  over `topic_uri` (via DNB SPARQL or a GND dump) can stamp a
  `subject_category_uri` field onto ~25% of records. Parked idea, medium effort.

## 6. Schema: what the interim index does wrong, on purpose

The interim core runs on Solr's **schemaless `_default` configset**
(`solr-precreate`), so every field was type-guessed to multiValued `text_general`.
Observed consequences — all verified against the live core:

- Exact **phrase queries work** on every field (`author:"Goethe, Johann Wolfgang von
  1749-1832"`, `topic_uri_str_mv:"https://d-nb.info/gnd/118540238"`), which is all
  the plugin's query builder emits. Position-increment gaps prevent phrases matching
  across two values of a multiValued field.
- **Prefix/wildcard queries on the IRI fields silently match nothing** (the IRI is
  tokenized; the prefix "https://d-nb.info/gnd/" is not a token). E.g. "all docs with
  any GND author" is not expressible.
- **Faceting on the base fields returns empty**; it works only on the auto-generated
  `*_str` copyFields (docValues strings) — which are **truncated at 256 chars**.
- Case-sensitive exact matching and no German analysis (no stemming, no decompounding)
  — irrelevant for the plugin's exact-value matching, inadequate for user-facing search.

For production: define an explicit schema. `string` (docValues) for ids, IRIs, codes,
and facet/filter fields; `text_de`-style analysis for searchable text (title, summary,
topic labels); keep an **exact-match string twin for every label field that consumers
match profile values against** (see §7 — matching semantics must stay exact), and keep
multiValued label/URI arrays position-aligned (§2) or replace that contract with
something better (nested docs) consciously.

## 7. What consumers rely on (the plugin's contract)

The TYPO3/docs plugin (bib-src) talks to the index read-only and relies on:

- **Endpoints**: `/select` and `/get` only — the public proxy (`solr/proxy.js`)
  allowlists exactly these paths and adds CORS `*`. Solr itself stays bound to
  loopback; `/update`, `/admin`, `/schema` are unreachable from outside. Keep this
  posture in production.
- **Lookups**: `id:<AK…>` (book details for clicked cards, Merkliste covers) and
  `onleihe_id:<mediaId>` (resolving clicked Onleihe links).
- **Recommendation queries**: exact phrase matches of profile values against
  label fields (`author`, `author2`, `genre`, `topic`) and IRI fields
  (`*_uri_str_mv`), OR/AND-combined, with `-id:"…"` exclusions for saved books.
- **Explanations**: the "why recommended" tooltips re-check profile facts against the
  *stored* field values of a returned doc — string-exact. Stored values must remain
  verbatim (analysis may normalize indexed terms, but not stored ones).
- **Indirection**: which profile predicate maps to which index field(s) is not
  hard-coded — it's declared in the vocabulary (`bp:linkedToIndex` with
  `bp:labelField`/`bp:iriField` in `bib-src/definitions/vocabulary.ttl`). **Renaming
  index fields in production is a one-line vocabulary change per field**, not a code
  change.
- **Covers** key on ISBN (via the inspira `/image/{isbn}` route) — the `isbn` field
  matters beyond bibliographic display.

One known content-level issue for recommendation consumers: the same work often
exists twice (print + Onleihe e-book) with **different ids and different ISBNs** —
per-id exclusion of saved books lets the twin back into recommendations. A
production index could add a work-level key (uniform title 240/130, or the 800/830
`$w` links) to enable work-level dedup; currently parked.

## 8. Import pipeline notes (if reused)

`shared.js` separates the MARC mapping (`mapRecord`) from transport: importers pass
`postBatch`/`postDeletes`/`finalize` callbacks. Details that took iteration to get
right: the import cursor is a **persistent high-water mark** per (target, dataDir) —
it survives completion so a later run only picks up new OAI files; batches are
POSTed pipelined (parse next batch while previous uploads) with exponential-backoff
retry; the cursor only advances after a batch's POST acks, so a crash resumes
without loss; OAI deletion markers are honored via `oai_identifier` delete queries.
`import-all.js` clears the cursor first (full reseed), `import-incremental.js`
doesn't.
